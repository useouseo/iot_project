# 시연과 발표 구성

## 5분 시연

1. README의 `server.py --demo`로 시작한다. 방문객 화면의 시연 배너를 먼저 설명한다. 세 가상 시설의 여유/보통/혼잡과 지도·목록 선택을 보여준다.
2. 휴대폰 폭 화면으로 바꿔 지도와 목록을 확인한다. 인원수·대기시간 대신 추정 단계만 표시하는 이유를 설명한다.
3. 관리자로 로그인하여 시설명·운영 칸 수를 바꾸고 지도에서 위치를 선택해 저장한다. 방문객 화면에 반영되는 것을 보인다.
4. 최근 2시간 입·퇴장 추이와 장치 상태를 확인한다. 데이터가 없는 구간은 0건이며 측정이 없었던 것인지 실제 통행이 0인지는 연결 상태와 함께 해석한다.
5. 시연 데이터 추가 후 변화와 2분 수신 단절 후 확인 필요를 보여준다. 실제 센서가 없으면 이 부분을 ‘센서 시연 성공’이라고 발표하지 않는다.
6. 실사용 모드는 별도 DB다. 장치 등록→발급 토큰 설정→시뮬레이터 실행으로 HTTP 수신을 입증하거나, 전체 컴파일/실물 검증 후 실제 ATOM을 연결한다.
7. 실제 방문객 주소를 준비한 경우에만 PUBLIC_URL 기반 QR을 인쇄·스캔한다. 개발 머신의 루프백 주소를 QR로 배포하지 않는다.

## 발표 7장 구성

1. 문제: 행사장 배치에 익숙하지 않은 방문객의 불필요한 이동과 대기.
2. 최종 요구사항: 탈부착·재사용·원격 통합·최근 통행량 기반 추정 단계. PDF의 주제 변경 이유를 요약.
3. 시스템: 센서/ESP32/HTTP/DB/웹 데이터 흐름. 카메라·얼굴 데이터 수집 없음.
4. 하드웨어: 두 세트 BOM 96,100원, 단일 센서 ROI 교대 측정과 설치 조건.
5. 소프트웨어: 중복 제거, 발생시각 기반 창, 품질·연결 표시와 관리자 설정.
6. 검증: 27개 API/로직 시험, 11개 C++ assertion, Chromium 사용자 흐름. 환경 차단·실물 미실행을 분리.
7. 한계/다음 단계: 통로 폭·동시 통행·배터리·모델 교정. 실측 전 수치 성능을 주장하지 않음.

## 예상 질문

- **인원이 정확한가?** 정확한 내부 인원을 표시하지 않는다. 최근 10분 통행량과 칸 수에 따른 단계다.
- **오차가 계속 누적되는가?** 현재 산출 창 밖의 기록은 제외된다. 다만 최근 창의 오차와 장기 체류를 알 수 없는 한계는 남는다.
- **왜 IoT인가?** 여러 시설을 센서에서 서버로 모으고 방문객·운영자가 떨어진 곳에서 함께 확인한다.
- **센서 한 개로 방향을 어떻게 구분하나?** VL53L1X의 ROI A/B를 교대로 측정하고 완전한 순서만 인정한다. 실제 설치에서 영역 분리와 샘플 주기가 충분한지는 시험해야 한다.
- **정전/통신 끊김은?** 장치는 64건 NVS 큐를 유지하고 서버는 중복 제거한다. 전송 불가가 2분 이상이면 방문객은 확인 필요를 본다. 큐 초과·24시간 초과는 손실로 보고한다.
- **배터리 몇 시간인가?** 아직 실측하지 않았다. 5000mAh 표기만으로 보장하지 않고 실제 평균 전력·자동 꺼짐을 시험한다.

담당 분담은 원문 계획을 참고하되 이 문서 작성으로 팀원에게 작업이 전송되거나 일정이 확정된 것은 아니다.
